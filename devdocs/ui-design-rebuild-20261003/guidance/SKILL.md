# LYStar UI Design

以资深设计师的工作方式完成任务：理解业务和使用场景，作出有取舍的结构与交互决定，让内容、排版、比例、组件和品牌形成一致的视觉语言，再检查实际使用结果。没有装饰不等于设计优秀；代码可运行、参考齐全或记录完整也不等于设计通过。

## 范围与执行方式

- 新建或结构重做按下面的决策链工作；只要方案就交付可复现的设计决定，不擅自实现。只要评审就给问题、位置、用户后果和修法。
- 局部改字、间距、颜色或状态直接保持现有结构与规范，检查受影响区域，不启动整套研究、比稿或评测。
- 项目数据、业务契约、品牌材料、组件和已有合格页面优先。区分用户要求、已知事实、设计判断与未确认假设；不把自行选的品牌色、常用程度或功能写成既定事实。
- 只询问会改变核心任务、范围或业务含义的缺口。普通设计取舍由执行者承担，不把每一步交给用户审批；不为完成流程强制创建文档或调用其他智能体。

## 1. 从任务与状态建立产品结构

先找使用者的进入原因，而不是先列组件。确认：用户此刻处理什么对象、想得到什么结果、做决定需要什么、当前状态允许什么动作。已有业务规则直接复用；缺少规则时不凭视觉参考创造权限、计算或状态转换。

把适用路径串起来：**进入 → 识别对象与当前状态 → 判断或输入 → 执行动作 → 得到结果 → 继续或返回**。考虑中断、取消和失败后的去向；已有记录的处理路径与新建路径分别梳理。多端共享业务含义，但按各端使用者和场景重排任务，不能把后台缩小成手机页。

据此决定信息架构：

- 高频任务提供直接入口；影响当前决策、需要立即处理的事项靠前。频率与紧急程度需有输入依据；没有使用数据时写成设计判断，不制造“常用”“智能推荐”等事实。
- 每个模块明确服务的用户问题、所需信息和下一步动作。共享对象或需要同时判断的信息放在一起；无关流程不因为接口齐全就常驻同页。
- 首屏围绕当前任务呈现对象、关键状态和入口；资料库、低频设置、历史细节按需进入。入口不等于把全部内容展开，功能可达也不等于功能都要上首页。
- 用任务发生的顺序与依赖安排模块，不按后台菜单、数据表或组件清单生成页面。不能说明放置理由的区块，先移出默认视图，而不是给它补标题和说明。

在画完整页面或写 UI 代码前，形成短结构草案：默认看什么、先做什么、哪些内容不在当前页、从哪里进入、如何返回。记在已有计划或设计记录即可。若草案只是功能清单，继续解决结构，不用视觉包装掩盖它。需要推演时看 [决策示例](references/design-examples.md)。

## 2. 让内容与交互支持决定

从真实内容安排字段和动作，不为组件插槽填文案。列表保留识别、比较与行动需要的信息，详情展开判断依据；同一事实可以在不同场景复用，但同一操作上下文不重复解释用途。

**内容准入直接执行：**标题下通用 description、按钮下操作复述、组件下安慰性提示默认不写。只有具体信息会改变用户判断、输入或恢复方式时才加入；输入限制放在对应输入处，错误说明问题与恢复动作，不在首页重复介绍整套流程。字段已表达上限、状态或后果时，不另加同义提示。文字润色不能让无用途内容取得展示资格。

关系由字段角色、标签、对齐与换行表达，不用成串的 `·` 把地点、时间、对象、状态串成一段。真实名称与原始文本里的符号保留。图标辅助辨认或操作，不代替必要标签，不为每个标题增加图标盒。

按任务选择承载位置：

| 需要 | 结构决定 |
| --- | --- |
| 扫描和比较大量同类对象 | 列表或表格；列顺序跟随判断顺序，搜索和筛选靠近结果 |
| 连续查看多个对象且保留队列 | 主从工作区，或可保持筛选与定位的详情入口；不靠 Drawer 外形判断它是否支持并行操作 |
| 短、单一、暂时的操作 | 项目已有弹窗或面板，独立草稿；取消不改保存数据，焦点回入口 |
| 长表单、跨阶段或需要独立访问 | 页面或已有工作流，按阶段安排内容；不把长流程塞入多层弹窗 |
| 同时核对相关数据 | 保留对照视图与对应字段，不为减少容器或表格数量拆走必要信息 |
| 移动端快速完成任务 | 按动作顺序组织单列内容、选择入口和操作区；资料选择进入相应步骤，而非默认铺满首页 |

仅设计本次需要的状态，明确用户看见什么、能做什么、怎样继续。适用的加载、空、禁用、校验、提交、失败和成功进入同一流程。失败保留输入，提交中防止重复，状态、数量与按钮一致；不以虚假按钮或静态成功图冒充可用交互。

## 3. 建立与任务相称的视觉品质

先读项目规范和目标平台。国内场景的导航、中文排版与移动约束按需读 [平台基线](references/china-product-baseline.md)。没有既定视觉方向时，根据内容与场景选定一套完整方向，不自动命名品牌、套主色或生成营销 Hero。操作页强调对象与效率，阅读页强调节奏与定位，品牌页让真实材料与主题承担表达；混合页面按主要任务分配注意力。

在结构成立后，观察适合当前设计问题的真实画面，再校准构图与细节。优先项目已有合格页面；不足时按 [参考入口](references/reference-map.md) 查看相关说明和实际原图。记录能迁移的关系及不适用部分，不照搬品牌皮肤、演示功能或示例数据。组件截图补控件经验，产品画面补层级与跨页关系，二者都不能替本项目决定任务结构。参考研究只解决当前缺口，不成为每次修改的固定成本。

把方向落实为统一参数，而不是逐个组件装饰：

- **构图与比例**：明确第一关注点、支持它的信息和下一步；按比较、阅读或输入所需分配宽度。留白分组而非填空，密度支持真实内容；主次靠位置、尺度、对齐和间距共同建立。
- **排版**：给对象标题、章节、正文、辅助信息、数据和操作明确角色；使用连贯的字号、字重、行高与基线。长中文、数字、单位和混排参与设计；不把图片像素直接当 CSS px / rpx。
- **节奏与几何**：组内与组间距离表达关系，列表行、输入和按钮保持一致尺度。圆角、分隔和表面跟随项目系统；容器用于真实分组、对象边界或独立交互，不把每块内容做成同权重卡片。
- **色彩与材料**：文字、背景、主操作、选择和状态各有角色及适当强度；整页的颜色关系协调，辅助信息仍可读。不用大面积主色代替重点，也不把品牌色机械限制为某个次数。
- **图像与动效**：内容、品牌或空间关系确实需要时使用，说明裁切与状态变化；普通操作反馈保持直接。资产来源、数量和承诺有依据，不增加自动轮播、漂浮等填空效果。需要生图时读 [资产规则](references/imagegen-ui.md)。

**本 Skill 的明确视觉边界：**不新增装饰性彩色圆角描边、彩色侧边条、渐变强调块、标题徽章、图标盒或重复容器来表达层级；不能用“品牌”“状态”“有语义”作为豁免理由。状态用清楚文字与项目已有状态样式，选中、错误和焦点用对应控件机制；这不是禁止必要输入边界或所有圆角。用户明确要求的不同方向按本次要求执行，不把新方向写回通用规则。进一步校准看 [内容与视觉校准](references/anti-noise.md)，但上述边界不依赖是否读取该文件。

先用结构和排版使主次成立，再检查色彩、图像与材质是否增强表达。减少装饰后仍需校准比例、密度、字面、行距、对齐和细节一致性；“全白、少字、无边框”不构成专业设计结论。

## 4. 实现后按实际结果闭环

实现沿用项目组件、token、路由、图标和状态 API；机制按需使用环境已有的 `frontend-ui-engineering`，文案按需使用 `shuorenhua`。核心判断由本 Skill 自身承担，不依赖可选 Skill 恰好被加载。局部组件的草稿和提交生命周期保持明确，相关资料不因同属一页就混入全局状态。

访问运行页面，分别检查三件事，不能相互抵消：

1. **任务成立**：用户能找到当前要做的事，信息足以决定，状态与动作匹配，低频内容没有挤走当前任务，返回保持所需上下文。
2. **视觉成立**：查看真实大小的首屏和后续内容；主次、比例、排版与节奏确实可见，必要文字可读，跨页语言一致，没有重复文案和上述装饰模式。不能只查 CSS 或凭“看起来专业”通过。
3. **运行成立**：在目标视口实际打开、取消、提交、返回与恢复；通过正常数据入口放入长名称、长位置、必要帮助及本次适用的空/错误状态。检查模块和子元素的边界、文本、图标与操作区，页面没有横向滚动不代表卡片没有向屏幕外溢出。

长文本按角色换行、截断或展开；关键信息必须可获取，不能靠裁掉溢出、缩小全页或改 DOM 造截图。桌面重排与手机安全区、键盘、实际触控热区、焦点和对比度按当前平台核对；可用时使用浏览器测量。没有运行条件就交付方案并列出未验证项，不称为实现或验收完成；浏览器小程序原型不证明微信运行或真机通过。

发现问题，先判断它属于任务结构、内容、视觉还是实现，再改对应责任位置并回查受影响部分。主任务不清回到结构，色彩问题回到视觉系统，溢出修内容与布局边界；不再给问题区叠一个卡片、提示或补偿性样式。角色协作时传递同一任务、保持项与核心约束，负责人查看实际产物，不采纳只有通过结论的自评。

## 交付与维护

交付当前结论、必要的结构/交互/视觉决定、可用产物入口和实际验证范围。复杂方案可用 [短设计记录](references/design-contract.md)，不强制填合同、写长报告或交付多套候选；参数应足以实现与检查。用户要求页面、动画或视频时交付对应可运行产物，不把代码、分镜或生成参考称为成品。

只有维护本 Skill 时读取 [维护边界](references/rule-catalog.md)、[结果评审](references/review-rubric.md) 和 [测试说明](evals/README.md)。测试保留首次输出、实际加载内容、运行证据和修正成本。格式检查证明可加载，单次成功证明该次覆盖，不能证明稳定或达到资深设计师水准；这些结论要由不同真实任务的成品质量和持续表现支持。修订优先改共同方法与责任位置，不把每次失败追加成独立禁令。
