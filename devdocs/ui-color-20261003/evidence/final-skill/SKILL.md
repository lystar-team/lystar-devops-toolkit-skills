# LYStar UI Design

完成有取舍的任务结构、交互与视觉设计，并检查实际使用结果。代码能运行、参考齐全、没有装饰或对比度通过，都不能单独证明设计优秀。

## 先选执行路径

先检查当前页面及直接相关的 `DESIGN.md`、主题/token、组件用法和业务契约。只读解决当前任务所需的部分；不要扫描整个仓库或先加载全部参考。

| 任务 | 直接执行 | 何时补充依据 |
| --- | --- | --- |
| 局部改字、间距、颜色或状态 | 读目标组件与相关 token → 修改 → 检查受影响区域 | 现有值、状态或规则有冲突时再查对应来源 |
| 已有系统中的新页面 | 读相邻合格页面与当前主题 → 简写任务结构 → 实现 → 检查 | 系统缺少本次所需的模式时才读一个对应参考 |
| 无系统的新页面或明确重做配色 | 确定任务 → 选一套适用基线 → 映射语义角色与状态 → 实现 → 检查 | 普通操作页直接取本地基线；定制品牌或基线未覆盖的问题才读 [配色方法](references/color-system.md) 的相关部分 |
| 方案或评审 | 给本次所需的决定，或问题位置、影响、依据和修法 | 缺口影响核心任务或业务含义时才问用户 |

**依据足够就开始实现。**项目主题、已核验本地基线或相关合格页面已覆盖当前问题时，停止外部搜索、翻图与多方案比稿。只有明确缺口才补一份相关材料；没有获取到就说明假设，不反复换站点。生图、独立评审和长设计文档均按本次需要启用，不是普通 UI 的前置步骤。

核心方法由本 Skill 自身承担。其他 Skill 只解决具体机制缺口，不沿依赖链全量读取；普通任务不读取维护、评测和历史报告。缺资料仍可提出有依据的结构与条件性视觉方案，不能声称已查看素材或已实现未知机制。

## 1. 从任务与状态决定结构

确认用户为何进入、处理什么对象、希望得到什么结果、判断需要哪些信息、当前状态允许什么动作。沿用业务事实源；不凭参考创造权限、金额、资格或状态转换。阶段保存、持久化与返回继续需要项目依据，新增机制标为建议或待确认。

串起适用路径：**进入 → 识别对象与状态 → 判断或输入 → 行动 → 结果 → 继续或返回**。根据当前状态先选下一步，再决定按钮；有关联记录或可恢复步骤时，提供该上下文入口。没有合法下一步就呈现结果或等待条件，不制造动作。期限与结果读取当前记录，不能套新建流程的通用说明。

默认内容围绕当前任务与必要判断。相关信息放在一起；资料库、历史细节和低频设置按需进入，保持必要返回上下文。高频、紧急与“常用”需有输入依据，没有数据时说明这是设计判断。多端共享业务含义，按使用场景重排任务。

新建或结构重做先简写：默认看什么、先做什么、哪些内容按需进入、如何返回。已有计划足够，不强制新建文件；若只是组件或功能清单，先解决结构。确需推演时看 [任务示例](references/design-examples.md)。

## 2. 让内容与交互支持决定

列表呈现识别、比较与行动所需信息，详情展开判断依据。通用 description、按钮操作复述和安慰性提示默认不写；只有信息会改变判断、输入或恢复方式才加入。限制放对应输入处，错误说明问题与恢复动作。已有字段表达的上限、状态和后果不重复解释。

对象、位置、时间与状态用标签、对齐、换行和文字角色表达，不用成串的 `·` 拼接；真实名称与原文符号保留。图标辅助辨认与操作，不代替必要标签，不给每个标题加图标盒。

| 任务需要 | 承载方式 |
| --- | --- |
| 扫描、筛选和比较同类对象 | 列表或表格，列顺序跟随判断顺序，筛选靠近结果 |
| 连续处理对象且保留队列 | 主从工作区或保留筛选定位的详情入口 |
| 短、单一、暂时的操作 | 项目已有弹窗/面板，独立草稿，取消不改已保存数据，焦点回入口 |
| 长表单、跨阶段、独立访问 | 页面或已有工作流，阶段与保存机制有依据 |
| 同时核对相关数据 | 对照区域与对应字段，不拆走必须同看的信息 |
| 移动端快速办理 | 按动作顺序单列，选择资料进入相应步骤，不铺满首页 |

实现本次适用的加载、空、校验、提交、失败与成功。失败保留输入，提交中防重复，数量、状态与动作一致。静态成功图和伪按钮不能冒充交互。

## 3. 先复用系统，再决定颜色与视觉

**颜色依据顺序：当前要求与品牌 → 项目有效的 DESIGN.md / token / 组件主题 → 匹配平台与任务的成熟设计系统 → 已核验本地基线。**不能因为是国内产品就自动蓝色或绿色。已有 Ant Design、TDesign、Arco 或 WeUI 时沿用该系统的语义 token、状态和主题机制；不混拼不同系统的默认值，不为配色新增框架依赖。

`DESIGN.md` 记录颜色角色、数值/引用和使用理由，实际主题实现决定运行颜色；两者冲突时核对作用域和当前要求，修本次责任点，不另建重复配置。已有规范只读取相关章节；需要跨页复用新设计系统时才在项目授权范围补充短规范，局部修改不生成整份文件。

**主色不等于所有用途的颜色。**先定义页面/容器背景、正文/辅助文字、主操作及其文字、链接、选择、输入边界/焦点、信息/成功/警告/错误文字与可选背景。操作填充色和小号状态文字分别取适合其背景的等级，浅深主题分别映射；颜色相同也保留角色。补本次实际用到的 hover/active/disabled 状态。

**日常配色直接取值：**无品牌、无组件系统的记录/表单操作页，可选本地 `td-light`，需要暗色则用配套 `td-dark`；明确选择微信服务视觉时才用 `weui-light`。这是起点，不覆盖已有要求。以本 Skill 目录为根执行 `python3 scripts/color_tools.py palette td-light --css`，再用 `check --preset td-light` 检查所选基线；脚本只读、零依赖，不必先加载脚本源码、完整色板或配色长文。映射到项目已有变量名，不建立平行主题。基线未覆盖、自定义品牌或需要解释适配时，才读 [配色方法](references/color-system.md) 的相关部分；使用不同基线时替换名称。

按真实前景和背景检查：普通文字至少 4.5:1；符合大字条件的文字和识别控件所需的图形/边界至少 3:1。透明色先叠到真实背景；检查实际使用状态。禁用控件与装饰分割线分别判断，不能把可读辅助文字当禁用文字。大厂默认值也需核对具体搭配；不直接把亮品牌色配小号白字或用降低透明度表示次要。对比度只证明可读性，仍需查看整页的协调与主次。

让颜色和其他关系一起成立：

- **构图与密度**：对象、关键状态与下一步清楚；宽度服务比较、输入或阅读，留白表达分组。
- **排版与间距**：标题、正文、辅助信息、数据和操作有稳定角色；长中文、数字、单位和混排参与设计。圆角、分隔与表面沿项目规范，容器对应对象、真实分组或独立交互。
- **色彩与材料**：中性色承载多数信息，主色引导操作与选择，功能色保持业务语义；不设机械的使用次数或面积比例。阅读和品牌页由真实材料决定表达，不默认生成营销 Hero。
- **图像与动效**：确有内容、品牌或空间关系职责时使用，安排裁切与状态反馈；需要生图时才读 [资产规则](references/imagegen-ui.md)。

**明确视觉边界：**不新增装饰性彩色圆角描边、彩色侧边条、渐变强调块、标题徽章、图标盒或重复容器来表达层级；“品牌”“状态”“有语义”不是豁免。必要输入边界、错误、选中和焦点沿控件机制，不能机械删除。用户明确要求的不同方向按当次要求执行。

项目无法覆盖构图或平台细节时，才按 [参考入口](references/reference-map.md) 或 [国内平台基线](references/china-product-baseline.md) 补相应内容。已有配色基线只解决颜色，不承诺所有页面共用同一布局。需要视觉参考时查看相关实际画面，记录适用关系，静态图不提供业务规则或 CSS px / rpx。

## 4. 检查实际结果，再交付

复用项目组件、路由、图标与状态 API。具体组件机制才按需读 `frontend-ui-engineering`，文案才按需读 `shuorenhua`。实现后在目标视口检查三件事：

1. **任务**：入口与进入原因一致，状态动作匹配，当前判断信息够用，返回保留所需上下文。
2. **视觉**：查看真实大小画面；构图、中文排版、密度、配色和跨页语言一致，必要文字可读，没有重复文案与明确拒绝的装饰。检查关键颜色对与实际状态，不用 token 清单替代画面。
3. **运行**：实际执行本次变更的打开、输入、取消、提交、返回或恢复；用正常数据入口检查长内容与适用空/错误状态。检查子元素溢出、遮挡与文本获取，不能靠裁剪、缩小全页或改 DOM 造截图。

验证范围跟随改动：颜色修改回查使用该 token 的受影响组件与状态，局部文案回查换行与行为；有新失败或新改动才扩大检查，不重跑无关全站流程。浏览器小程序原型不证明微信或真机通过。无运行条件就说明未验证项，不称验收完成。

问题回到任务、内容、token 或组件的共同责任点修正，不叠加补偿性提示/卡片。达到当前目标与必要验证后停止。交付结论、依据、可用入口与实际验证范围；方案、源码、截图、运行页面和生图资产分别说明。
