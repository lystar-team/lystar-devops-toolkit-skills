# UI/UX Skill 测试

测试对象是实际设计行为与成品，不是指令关键词、模板长度或文件数量。格式/引用/安装检查证明可加载；业务任务、运行页面与审阅证据才说明当前覆盖的质量。使用 [结果评审](../references/review-rubric.md) 判断，不把反装饰通过等同于专业、美观或稳定。

## 按授权完成一次有意义的测试

1. 明确获准的智能体数量、任务范围、工作区和工具。没有要求版本对照时不强制双会话 baseline/guided，不为普通开发加载评测。
2. 用真实业务形态、原始字段、用户与目标平台给出任务。保留明确用户要求，但不额外提供预期布局、正确文案、怀疑的失败点或改稿答案。
3. 记录实际加载的核心、所用参考与其他能力；保留第一次完整源码与画面，再运行当前任务需要的打开、输入、提交、取消、返回和失败恢复。测试数据走正常数据入口，不用临时改 DOM 造截图。
4. 查看任务结构、内容与视觉、实现三种结果；记录具体问题、依据、用户后果和修正。专业品质须包含构图、排版、比例、节奏与视觉一致性，不能只统计功能和禁用元素。
5. 用反向场景检查有没有过度约束：必要帮助、多表核对、长流程、品牌材料与局部改字应保留自身职责。发现问题回到对应方法，不把每项反馈追加成禁令。
6. 负责人查看成品与证据，再决定采用或修订。生成者自检不叫独立审阅，单个智能体连续任务不叫独立多次抽样；未执行、工具失败与视觉失败分别写明。

“完整测试”表示获准范围覆盖核心、相关参考、短路径与新建/评审行为，并有可回查的实际证据，不表示每种业务、每个平台或真机均通过。可先用不同任务检查通用方法，再用真实项目持续验证稳定性。

## 成本与证据

记录任务、实际加载内容、工具与目标视口、首次产物、发现的问题、修正范围、实际操作及未验证项。工具次数、时长或返工量可用于观察执行成本；没有旧版同条件对照时不写效率提升或收益百分比。

若用户明确要求对照，才固定 prompt、输入、模型/设置、工具、起始代码、主题与视口，只改变指令版本。旧版是当时实际指令，不以“完全不加载 Skill”代替；不把相互看到答案的产物称为盲评。只有真正未参与调整且实际运行的场景，才能作为留出验证证据。

## 资源与落盘

既有 `fixtures.schema.json`、`results.schema.json` 保留，用于需要机器读取的固定场景。fixture 描述任务/输入与视口，result 描述实际产物和发现；它们不要求所有测试都填写 JSON 或使用 baseline/guided。简短或单智能体测试可以直接保存输入、源码、截图与 Markdown 报告，未运行不预填通过。

测试新产物使用隔离临时工作区，不改生产页面、Skill 源码或其他配置。用户要求保存测试成果时再接收对应产物。普通维护不新增测试框架或依赖；本地浏览器检查遵守本次具体授权，不扩展成真实业务 E2E。

## 已有材料的范围

- `scenarios/ui-cn-inspection-report`：中文巡检 Web 样例与本地模拟提交。含运行画面和路径证据，没有旧版对照，不证明整体设计质量或小程序真机可用。
- `scenarios/ui-cn-stock-transfer`：固定场景输入，尚未执行；不能称为已通过。
- `references/examples/index.html`：十组十五张参考画面的浏览入口。筛选和原图入口检查只验证资源可用，不验证新页面设计能力。

历史记录按当时事实保留，不重写为重构后的通过结果。稳定、高效、资深设计师级别等结论须由持续成品表现支持，不由一次测试或自评分数宣告。
