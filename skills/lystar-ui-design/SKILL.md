# LYStar UI Design

负责从真实产品约束到可运行界面的完整视觉链路。图像生成负责把审美方向变成可见目标，源码、接口和需求负责业务事实。

## 任务模式

先判断本轮类型：

- `build`：新页面、新应用或多页面统一。
- `major-redesign`：信息结构或视觉语言明显重做。
- `modify`：局部布局、样式、交互或响应式调整。
- `review`：只读评审；用户同时要求修复时再进入对应实施模式。

只处理用户明确范围。不要借 UI 任务改业务规则、接口、权限或无关页面。

## 读取真实材料

开始前读取直接相关的页面、组件、样式入口、设计变量、真实文案、品牌资产和用户参考。确认：

- 使用者、核心任务和最高频操作。
- 必须保持的业务内容、状态、交互和技术约束。
- 页面属于操作型、消费/内容型还是表达型产品。
- 当前最影响理解、操作或质感的问题。
- 目标桌面、移动端或固定画布尺寸。

已有项目级 `DESIGN.md` 时读取并沿用；没有时按下节任务类型决定合同范围，不默认创建文件。只有用户明确要求交付设计规范，或已确认维护一个反复使用的项目界面规范时，才创建或修改项目级 `DESIGN.md`。设计合同不替代需求、业务事实、组件 API 或项目 `AGENTS.md`。

## 设计合同与规则归位

`build`、`major-redesign`、结构性 `modify` 和完整 `review` 读取 [设计合同](references/design-contract.md)，形成当前任务的短合同。局部文案或样式修改只确认相关边界；新增或改变展示字段时列明受影响字段的允许范围，不因字段变化填完整结构合同，也不借此重做页面。结构性任务的合同至少回答：

- 适用范围、读者和读者要完成的任务。
- 主任务留在何处，次级任务从哪里进入、由什么位置承载。
- 允许展示的内容与字段、必要帮助说明，以及支撑它们的事实、限制和未决项。
- 首屏构图假设、可用 token / 组件 / 资产，以及目标视口的变化。
- 必须保留的行为、需要避免的反模式和本轮验证目标。

合同属于任务上下文，不是页面上的说明卡片。缺少依据且会改变展示范围或操作流程时，向用户确认；不把原始接口字段全部当成展示需求。

把规则放到能稳定约束它的最窄位置：读者任务、层级和构图进入 `lystar-ui-design` 判断；项目事实、品牌资产和组件 API 留在项目权威文件；可复用机制进入项目 token 或组件；可以可靠静态识别的问题进入 lint / validator；浏览器、截图和运行环境问题留在验收工具。不要把一次截图、一次评论或一个项目的品牌选择直接升级成全局规则。

规则新增或修订时读取 `references/rule-catalog.md`。只在有可回溯来源、明确范围、例外和可复现证据时采纳；无法泛化的反馈记录为覆盖缺口或当前任务意见。

## 内容准入

新增可见文字前，判断谁需要它、缺少它会影响哪项理解、判断或操作；有用途再写，不用文案填满组件插槽。

- 标题、字段与动作已表达用途时，不补 description；删除重复标题、罗列按钮功能或展示开发成果的说明，不换词保留。
- 实现机制、接口调用和代码组织不进入业务页面。必要输入限制、动作后果、错误帮助与可访问性描述应保留，内容须来自需求或项目事实。
- Contract 列明允许展示内容与字段。内部 ID、批次号、重试和调试值未列入允许范围就不展示；改名、格式化、拼接或放入 Tooltip 不构成例外。段落、空状态和提示框遵守同一内容边界。
- 业务编号与专业术语是否展示取决于读者任务；运维或开发工具确有需要时，在 Contract 中明确用途与字段，不把业务后台的默认范围套给它。
- 本规则约束展示，不授权删接口字段、改数据结构或权限。保留本次范围外的既有内容，不因局部改字清理整页。

## 任务与承载位置

生成视觉稿和写代码前，确定主任务、次级入口和承载位置。普通业务管理页围绕主要工作任务组织；功能完整要求入口与路径可用，不要求所有功能同时展开。

| 任务特征 | 候选位置 | 避免 |
| --- | --- | --- |
| 高频扫描、筛选、比较、列表选择 | 主页面或主工作区 | 把主要工作藏进弹窗 |
| 当前对象的短操作，有完成与取消边界 | Dialog | 长流程、大范围导航或弹窗套弹窗 |
| 需保留列表视觉上下文的查看或轻编辑 | Drawer / 项目已有侧面板 | 仅凭侧滑外形认定它不阻塞底层操作 |
| 长表单、多步骤、独立链接或持续工作 | 独立页面或项目已有工作流 | 为少建路由把内容塞进弹窗 |
| 同一对象的互斥视图或工作区分类 | Tabs | 用 Tab 包装无关管理模块 |
| 单条记录的短补充 | 展开行或折叠区 | 嵌入完整子管理系统 |
| 需要同时核对相关数据 | 主从布局或多表对照 | 无比较需求的同权重堆叠 |

沿用项目组件与交互模式，按任务选择，不为使用 Dialog 或减少表格数量改坏流程。

- 不因接口返回多个数组就创建多个表格；同一资源的状态分类先判断筛选或互斥视图是否足够。
- 多个区块各有筛选、分页、编辑和提交过程，是检查任务边界的信号，不是自动拆页的条件。无共同任务的完整管理区不因同属一个模块而堆在一页。
- 对账、主从编辑和明确的工作台任务可以多表并存；检查数据关系、可用空间与操作路径，不设“一页一表”的硬门禁。
- 卡片包裹、CSS 隐藏、换组件名称或拆文件不证明完成分层；次级内容收起后必须保留可发现的入口。

## 视觉生成

`build` 和 `major-redesign` 默认读取并使用当前环境内置的 `imagegen` Skill 与图像生成 Tool：

- 单页面默认生成一张主视觉 UI mockup。
- 多页面或设计系统任务，在主页面之外单独生成一张 UI Kit 视觉板。
- 页面需要插图、纹理、主图或场景资产时，每类资产单独生成。
- 重做现有页面时，把当前页面截图作为编辑参考，明确写出保持项与变化项。

以下情况默认不生成：

- 简单间距、颜色、字号、边框或控件调整。
- 已有设计稿足以直接还原。
- 只读 `review`。
- 生成图不会改变当前实现判断。

默认只生成一个主方案。结果存在明确问题时做一次定向修改，不批量制造候选。

## 强视觉任务

Landing Page、品牌页、作品集、活动页、游戏界面或重大视觉重做，需要更强艺术方向时，先读取 `design-taste-frontend`，取得一份明确视觉方向，再调用 imagegen。

后台、Dashboard、表单、表格和普通局部修改不调用它，除非用户明确指定。

## 生成前简报

调用 imagegen 前形成以下简报：

```text
产品与用户：
核心任务：
页面结构与真实内容（沿用设计合同中的主次任务、入口和允许展示范围）：
视觉方向：
一个识别点：
现有品牌、字体、颜色与组件约束：
目标画布：
必须保持：
禁止出现：
```

详细提示词格式见 `references/imagegen-ui.md`。生成图中的文字尽量少；关键业务文案在真实代码中准确实现。

## 从图像提取视觉合同

生成结果通过检查后，把视觉合同补入原设计合同，再写代码；不从图中重定任务、字段与入口：

```text
页面任务：
信息层级：
布局与网格：
排版角色：
颜色角色：
组件、状态和图标：
图片或插图用途：
桌面与移动端变化：
必须保持的业务内容：
```

图像只决定构图、密度、排版、颜色、几何、媒介和节奏。以下事实必须回到需求、源码和接口：

- 文案、数据、状态、权限和业务动作。
- 组件是否真实存在、交互是否可实现。
- 错误、空、加载、禁用和选中状态。
- 响应式断点与实际内容长度。

不实现生成图里虚构的指标、功能、评价、导航或品牌信息。

## 映射到实现

- 沿用项目技术栈、布局、组件、图标、字体和 token。
- UI Kit 视觉板要落实为项目原生 token、组件和状态，不能把整张图当组件。
- 组件与状态的责任划分遵循 `yean-develop-style`；局部拆分与公共抽象分开判断，拆文件不能替代本 Skill 的任务分层。
- 操作型产品优先扫描、比较、输入、状态和连续操作。
- 消费与内容产品优先真实主体、决策信息、图文关系和阅读节奏。
- 表达型产品可以加强构图、图像和动效，但行动路径必须清楚。
- 页面和组件实现按需读取 `frontend-ui-engineering`，把可访问性、状态、响应式和组件机制落实到代码。
- 需要外部 Web Interface Guidelines 审查时读取 `web-design-guidelines`；不要用它替代读者任务和构图判断。
- 真实页面、截图、a11y、console 或错误证据使用 `agent-browser`；公开页面的 CSS / DOM 事实提取按需使用 `lystar-web-restore`。
- 页面和组件文案同时读取 `shuorenhua`，保留真实文案、数字、条件和责任主体；内容准入由本 Skill 判断，文案润色不扩大展示范围。


## 视觉边界

没有产品依据时避免：营销式 Hero 用于后台、卡片套卡片、紫蓝渐变科技感、装饰性图标盒、所有控件胶囊化、超大标题挤压内容、假数据、多个识别点争抢注意力。

熟悉符号优先使用项目图标库或 Lucide。业务工具保持克制密度；品牌和表达场景才使用更强媒介和动效。

## 验收

`build`、`major-redesign` 和明显可见的 `modify` 完成后，启动真实页面并检查目标视口截图。交互有改动时，检查相关入口、打开、取消及状态归属；提交只在已授权的数据与环境范围内验证。截图不证明交互完成，这些检查也不构成业务 E2E 授权；E2E 与测试范围遵循 `yean-develop-style` 的“验证”一节。环境不可用时说明缺少的页面证据，不用构建结果替代。

对照设计合同检查：

- 信息层级、布局比例和首屏构图；主任务与次级入口是否成立，多表是否服务共同任务。
- 可见内容是否有用户用途并处于允许范围；description 是否冗余，必要帮助是否保留。
- 字体、颜色、边界、圆角和组件状态。
- 真实内容是否溢出、遮挡或导致布局跳动。
- 目标视口的核心动作是否清楚可用。
- 生成资产是否已进入项目正式路径。

生成图与业务可用性冲突时，以业务和真实页面为准，并保留视觉方向中仍成立的部分。

## 评估与维护

普通 UI 任务沿用最小的真实页面验收，不默认运行完整 eval、E2E 或全仓构建。维护本 Skill、验证反复出现的设计问题，或比较一条新规则是否有效时，读取 `references/review-rubric.md` 和 `evals/README.md`。

固定场景冻结 prompt、输入、起始代码、模型与配置、工具、视口和其他加载规则。修订已有 Skill 时，baseline 使用旧版本，guided 使用候选版本；独立会话保留各自第一次交付及实际加载文件，不把旧版失败或改稿答案交给新版。源码、截图、相关交互证据与人工意见分别记录；不把小样本改善写成整体质量承诺。

评审反馈按以下顺序处理：

1. 判断它是否能跨场景复现，并保留最小证据。
2. 确定它属于设计判断、项目 primitives、确定性检查还是验收工具问题。
3. 只修改对应责任位置，并重新运行受影响的场景。
4. 单个模型或单次输出的偶发失败暂不升级为全局规则。

## 交付

简短说明视觉基准、实现范围、使用的生成资产、真实页面验证和未验证项。用户只要方案或评审时停在对应结果，不修改代码。
